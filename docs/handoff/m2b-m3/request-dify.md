## 1. 背景与范围

本项目是面向已登录、已授权渠道经纪的保险经纪 AI 智能体。M2a 已在本地离线完成 Dify 调用抽象、
出口合规守卫和工具网关（见 [M2a-2 契约与自验收](../../m2a2-offline-tools.md)），**尚未连接任何真实
Dify 或模型**。当前应用检测到 Dify 地址或密钥配置时会拒绝启动，要等本单环境到位后才解除。

M2b 需要一套独立的 Dify 实例，接入 DeepSeek，部署三个应用：

- `broker_assistant_chat`（Chatflow）：意图识别与统一入口
- `proposal_extract`（Workflow）：参数抽取
- `compliance_guard`（Workflow）：合规审查

各应用的节点、输入输出和安全边界见 [Dify 工作流实施计划](../../dify-workflow-plan.md)，本单不重复。
M3 知识库在同一实例内建数据集，资料规范见 [kb-intake.md](kb-intake.md)。

隐私／法务审批通过前，只使用合成数据或经负责人确认的脱敏样本，不接入真实客户资料。

## 4. 后端密钥配置方式

原则：**密钥只放业务后端的受控配置**。不进入前端、代码库、工作流变量、prompt、日志、审计正文、聊天或邮件。

| 密钥 | 持有方 | 配置位置 | 交付方式 |
| --- | --- | --- | --- |
| 三个 Dify 应用的 API Key | 业务后端 | 公司密钥管理系统（名称待确认），运行时注入后端进程 | 由有权限的人直接录入密钥管理系统，只把引用名告诉我方；请勿发送明文 |
| DeepSeek 调用凭据 | Dify 模型供应商配置，或自部署推理服务 | 仅 Dify 管理员可见 | 不经过我方 |
| 工具调用签名材料 | 业务后端按次签发 | 无长期密钥：后端签发最长 5 分钟的 `actor_token`，请求用 HMAC-SHA256 签名（见 [M2a-2 鉴权](../../m2a2-offline-tools.md#鉴权与后端映射)） | 无需交付 |

请确认：

1. 密钥管理系统名称及注入方式（环境注入、挂载文件或其他）— 待确认
2. 轮换周期、泄露时的吊销流程及负责人 — 待确认
3. 测试与试点是否使用不同密钥（建议分开）— 待确认
4. Dify 运行记录通常会显示工作流输入变量（以实际版本为准）。`actor_token` 作为输入传入，虽只有 5 分钟有效，
   仍需确认运行记录的访问范围，或约定其他传递方式 — 待确认

说明：当前原型只预留了单一的 Dify 地址与密钥配置项，且在 M2a 阶段会拒绝启动。按三个应用分别配置密钥，
属于 M2b 的后端改动，环境到位后实施。
