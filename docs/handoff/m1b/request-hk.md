# M1b · 香港 Python 对接资料请求单

起草：2026-09-23 · 状态：待香港回复 · 回复时限：待双方约定

## 背景

我方准备把香港现有的保司 Python 脚本接入统一任务系统，第一步只打通**一家保司、一个产品**（M1b）。我方已有调用契约草案和本地适配骨架，但**目前没有连接任何香港端点，也没有声称支持任何真实保司**。

本单列出开始对接需要的资料。每项都写了要什么、为什么要、用什么格式、建议谁提供、哪些东西不要发。不确定的地方请直接写"未知／待查"，不要估算。

## 请先看：三类东西不要发

1. **明文凭据**：门户账号密码、验证码、MFA 种子或备份码、Cookie、会话 token、API key、私钥。凭据只用引用名 `credentialRef` 表示（见 R10）。
2. **真实客户资料**：姓名、证件号、电话、邮箱、地址、真实保单号或申请号。样本按 [sample-spec.md](sample-spec.md) 脱敏，最好直接用虚构资料生成。
3. **不经聊天工具或邮件正文传代码、样本和配置**。请走双方约定的受控渠道（渠道待确认）。

## R01 代码访问方式

- **要什么**：脚本所在的仓库或目录；我方可用的访问方式（只读仓库权限、受控远程环境或代码快照包，三选一）；本次对接的基准版本（commit，或快照包的日期与 sha256）；一份目录树。
- **为什么**：先做静态检查——入口、依赖、有无硬编码凭据、固定下载文件名、共享浏览器会话、无限重试、本机路径依赖——再决定每个脚本"直接复用／加封装／需修复／暂缓"。
- **交付格式**：只读权限经受控渠道开通；或代码包＋sha256。
- **建议提供人**：代码维护人。
- **不要**：包含凭据、Cookie、已下载真实客户 PDF 的目录（请先排除）；只给截图。

## R02 入口函数

- **要什么**：首家保司／产品对应的入口文件和函数（或命令行入口）；参数与返回值说明；同步还是异步；执行中的副作用（在门户会提交什么、会写哪些本地文件）；现有的 API、队列、任务状态、日志或鉴权机制（有的话我们优先复用）。
- **为什么**：决定封装方式（Python 内部调用、独立进程或扩展现有服务），避免另搭一套相互冲突的任务管理（契约 §1）。
- **交付格式**：一页说明＋函数签名；已有 HTTP 或队列接口的，附接口说明和一组脱敏的请求／响应示例。
- **建议提供人**：代码维护人。
- **不要**：把用户文字直接拼进 shell 命令的调用方式——我方不会这样接入。

## R03 运行命令与依赖

- **要什么**：Python 版本；依赖锁定文件；浏览器及驱动的名称和版本；是否依赖桌面／图形界面、字体、本机固定路径；需要的环境变量**名称**及含义；一条能复现样板运行的命令。
- **为什么**：在获准环境复现一次样板运行，确认依赖可控、可重建。
- **交付格式**：文字清单＋依赖文件原件。
- **建议提供人**：代码维护人。
- **不要**：环境变量或配置文件里的真实值，用 `<占位>` 替代。

## R04 运行机器及能否长期运行

- **要什么**：当前运行机器类型（个人电脑／服务器／虚拟机）和操作系统；网络能否接受入站请求，还是只能主动出站；能否长期运行（全天或工作时段）；断电、断网、系统更新、账户隔离和远程维护怎么安排；维护人（写角色即可）。
- **为什么**：现有香港电脑适合做初步验证，但能不能作为长期执行节点要单独确认。这一项也决定我们用同步 HTTP 还是异步队列／轮询。
- **交付格式**：逐条回答上面的问题。
- **建议提供人**：运维＋代码维护人。
- **不要**：远程登录密码、VPN 配置文件或密钥。

## R05 首家保司／产品及官方版本

- **要什么**：从**已经能稳定运行的脚本**里选一家保司、一个产品；门户上显示的官方产品全称、产品代码（如有）、版本号或生效日期；版本号在门户页面和 PDF 上分别显示在哪里；选择理由（使用频率、人工耗时、账号可用性、字段复杂度等）；门户使用的授权主体和允许范围。
- **为什么**：M1b 只打通一社一产品。确认快照和 PDF 核验都绑定官方版本，版本对不上的文件不能交付。
- **交付格式**：按 [启动包](../../phase-01-start-pack.md) §2.1 填一行，附版本出处的脱敏截图。
- **建议提供人**：业务负责人＋产品专家。
- **不要**：只写口头简称或别名；一次给多个产品（其余产品在首个产品通过后逐个接入）。

## R06 真实字段与约束

- **要什么**：该产品门户表单的全部字段，包括官方标签、控件类型、是否必填、类型与单位、可选值或范围、跨字段限制、年龄口径（足岁、下次生日还是出生日期）、门户或脚本自动带出的默认值，以及字段在 PDF 上的显示位置。每个字段给一组有效值、一组无效值。
- **为什么**：用来建真实 schema 和确认页，也是 PDF 逐项核验的依据。像"非吸烟"这样的明确否定值必须能和"没填"区分开。
- **交付格式**：按 [启动包](../../phase-01-start-pack.md) §5 参数映射表填写，附门户表单页的脱敏截图。
- **建议提供人**：产品专家（业务含义）＋代码维护人（脚本实际填了哪些字段、怎么填）。
- **不要**：凭经验推测的范围或默认值；不确定就写"待查"。

## R07 PDF 获取方式

- **要什么**：PDF 是直接下载、门户临时链接、邮件发送还是其他方式；下载目录和文件名规则（是否固定文件名、多个任务是否共用目录）；临时链接有效期；脚本怎样判断"下载完成，而且是这次任务的文件"；PDF 能否提取文字（还是扫描图片）；PDF 上是否印有产品版本、门户参考编号、生成时间；按保司使用条件，文件能否留存、能否由我方代理下载。
- **为什么**：交付前要核验：确实是 PDF、来源和版本一致、参数一致、不是登录页、没有和其他任务串文件。固定文件名或共用下载目录是串文件的常见原因。
- **交付格式**：文字说明＋R11 中的脱敏 PDF。
- **建议提供人**：代码维护人。
- **不要**：带签名或令牌的真实门户链接。门户临时链接也不能当作长期接口使用。

## R08 登录／MFA 流程

- **要什么**：登录方式（账号密码、SSO、证书或其他）；MFA 类型（短信、验证器、邮件或其他）和由谁接收（写角色）；会话有效期；脚本怎样发现会话失效或被跳回登录页；目前哪些步骤仍需人工；测试时能否可控地触发 MFA 和会话过期；门户使用条款是否限制自动化操作。
- **为什么**：登录失效和 MFA 一律转人工处理，不绕过（契约 §5 的 `AUTH_REQUIRED`／`MFA_REQUIRED`）。验收也需要能复现这些失败场景。
- **交付格式**：流程说明，可附脱敏截图。
- **建议提供人**：代码维护人＋账号管理人。
- **不要**：验证码、MFA 种子或备份码；任何绕过验证码或门户风控的方法。

## R09 单账号并发限制

- **要什么**：同一门户账号能否同时开多个会话；新登录会不会踢掉旧会话；有没有频率限制或锁号规则；首期能用几个账号；账号是否多名经纪共用；一个真实账号是否只对应一个 `credentialRef`。
- **为什么**：我方已按 `credentialRef` 让同一账号串行执行，但如果两个不同的引用其实指向同一账号，本地无法识别（契约 §4）。同账号并发互踢会让结果变得不确定。
- **交付格式**：逐条回答。
- **建议提供人**：账号管理人＋代码维护人。
- **不要**：账号名或登录名本身，用引用名代替。

## R10 `credentialRef`

- **要什么**：脚本现在把凭据放在哪里（只描述方式，例如写在代码里、环境变量或密钥库）；建议的受控密钥存储及负责人（角色）；每个真实账号一个稳定的引用名；轮换与吊销流程。引用名的命名约定待双方确认。
- **为什么**：任务只携带 `credentialRef`，凭据本身不能进入提示词、日志、审计正文、聊天或代码库。
- **交付格式**：引用名清单＋管理流程说明。
- **建议提供人**：账号／密钥管理人。
- **不要**：**任何明文密码**。如发现脚本里写死了凭据，请告诉我们位置并先移出，不要把内容发给我们。

## R11 3–5 组脱敏样本

- **要什么**：同一产品、同一官方版本的 3–5 组"官方输入 ↔ 官方 PDF"，覆盖普通参数、另一缴费方式或币种、合法的年龄或金额边界值。可选：1 组被门户拒绝的输入及拒绝提示；1 份会话失效时脚本实际拿到的内容（例如登录页）。
- **为什么**：这是确定性核验规则的依据，也是验收基准。系统不计算金额，只核对输入参数和官方 PDF 是否一致。
- **交付格式**：按 [sample-spec.md](sample-spec.md)。
- **建议提供人**：产品专家（确认组合有效）＋代码维护人（生成文件）。
- **不要**：真实客户资料；为凑数而虚构的产品范围；不是门户官方生成、经过重新排版或改过数字的 PDF。

## R12 异常返回、耗时与维护安排

- **要什么**：脚本现有的异常、退出码和日志格式；怎样区分"执行前参数被拒""登录失败""超时""结果未知"；门户拒绝参数是否一定发生在生成之前；能否在门户按参考编号查到已生成的计划书（用于中断后核对）；平均耗时与最长耗时；维护人和人工兜底联系人（写角色）。
- **为什么**：用来对应契约 §5 的错误码。只有明确"门户还没生成任何东西"的拒绝才能自动结束任务并释放账号，其余一律转人工。中断恢复时要先在门户核实结果，不能直接重跑。
- **交付格式**：脱敏的错误样例＋说明。
- **建议提供人**：代码维护人＋运维。
- **不要**：带凭据、Cookie、会话或门户内部链接的原始日志或堆栈，请先脱敏。

## 收到资料后我方会做什么

1. 静态检查代码，把每个脚本归入"直接复用／加封装／需修复／暂缓"（契约 §7）。
2. 理解副作用和授权范围后，在获准环境复现一次样板运行。
3. 确定同步或异步接入方式，实现鉴权、执行尝试持久化、真实字段核验和受控文件下载。
4. 按 [acceptance-cases.md](acceptance-cases.md) 逐条验收。全部通过之前，M1b 保持"未完成"，也不会对外说已支持该保司。

- 资料之后有变化（产品换版本、脚本改动）请注明变更日期和影响范围。
