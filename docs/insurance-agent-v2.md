# 保险智能体落地方案 v2 · 工程评审稿

修订日期：2026-09-21。依据：用户提供的 v1，以及本次可读取的官方资料。本文是方案与开发任务书，未部署系统、未连接保司门户、未完成法务评审或真实账号联调。

后续补充：用户已说明有多家保司可用的 Python 文件。当前实施以《分阶段交付计划 v1》为准，先盘点并复用已有代码；本文保留为工程评审记录，其中从零初始化 RPA 和技术栈的假设不再直接用于排期。

## 1. 决策摘要

新建独立的渠道服务 Dify，候选部署地为香港；APP/H5 作为首期业务入口，微信客服作为后续官方单聊入口，企业微信客户群先承担入口分发和已核实的固定运营能力。业务后端负责身份、授权、任务、文件和审计，Dify 负责知识问答与参数抽取，RPA 负责在获授权的保司门户生成官方计划书。

首期交付闭环：经纪登录 → 选产品 → 填写或抽取参数 → 确认参数快照 → 创建异步任务 → RPA 生成 → 核对官方 PDF → 经纪鉴权下载。

保留 v1 的核心方向：独立 Dify、官方计划书、模型不计算利益演示、每产品独立 schema、从一家保司和少量产品起步。调整关键依赖：客户群双向 AI 不作为首期交付前提；鉴权、隔离、审计与任务持久化提前到 P0/P1。

## 2. v1 中必须修正的前提

| v1 表述 | v2 处理 | 对交付的影响 |
| --- | --- | --- |
| 服务经纪，所以投保建议监管红线基本不适用 | B 端工具的用途与职责可以收窄，但不能据此认定监管责任豁免；要评估实际输出及其如何用于销售 | 产品建议、适合性判断和对客材料保留经纪复核 |

| 客户群关键词命中可回调后端，接 Dify 动态回复 | 本次未取得该链路的官方接口依据，不能列作现成功能 | P0 改为 APP/H5 问答；群内提供已核实的入口 |
| 客户群 webhook、aibot 能直接推业务通知 | 不能将不同机器人和群类型的能力互相套用；需逐项核实群类型、接收人、发送权限和额度 | 首期可靠通知落在 APP 任务中心，其他渠道按能力接入 |

| Dify 内置 `enforce_compliance()` | 将其明确为本项目自建的策略服务名称，不能当作现成保险合规功能 | 需要规则、版本、测试集、拦截和人工升级流程 |
| 官方 PDF 所以数字绝对准确 | 官方来源可验证，但参数、产品版本、登录会话和返回文件仍可能错配 | 交付前比对已确认参数与 PDF 关键字段 |
| mock 换真实 adapter 即上线 | mock 只能验收软件链路；真实门户还有授权、登录、异常、文件与并发验收 | 将演示验收与真实试点验收分开 |
| AB-Bot 大概率全用 Hook、自己算数、只有微信群 | 未提供可靠竞品证据 | 改成待调查项，不据此作产品或销售结论 |

香港保监局网站刊载的《Conduct in Focus》AI 讨论文章明确指出，部署聊天机器人的保险人或中介不能把服务责任推给机器人；文章亦注明是作者观点，不能将其当作针对本项目的正式监管裁定。适用义务仍需结合实际业务判断。[保监局文章](https://www.ia.org.hk/en/legislative_framework/Conduct_in_Focus_Issue_07_%28Article_03%29.html)

企微核验限制：本次企业微信开发者站点通过网页工具读取失败，浏览器读取亦超时。上述客户群链路是“尚未验证、不可承诺”，不是声称已查遍截至本日的全部开放能力。正式接入前，以官方文档、企业后台实际权限和测试群收发结果共同验收。

## 3. 架构与责任边界

```text
APP IM / H5 / 微信客服 / 经验证的其他入口
                  │
             通道适配与业务网关
       验签、去重、身份映射、授权、限流
                  │
          ┌───────┴────────┐
          │                │
     Dify 渠道应用       业务服务
     问答、抽参数        schema、确认、任务、进度
          │                │
     获准知识库          持久化任务库 → Worker → 保司 adapter
          │                │
     策略检查服务        PDF 核验 → 私有文件存储 → 鉴权下载
          └───────┬────────┘
              审计与监控
```

以上为本项目设计，不代表 Dify 自动提供这些业务模块。

- **Dify**：知识检索、带来源的回答、参数候选提取和受限工具编排。无需用 Dify 执行简单表单的每一次提交。
- **业务后端**：可信身份、产品可用性、经纪与客户授权关系、参数校验、确认记录、幂等、任务状态及下载权限。不能把这些判断交给提示词。
- **RPA Worker**：使用凭据引用取得授权会话，填表、获取和校验文件。验证码、MFA 或页面异常进入人工处理状态。
- **策略服务**：本项目自建，检查输入、检索范围、工具调用权限和最终输出；审查失败或服务不可用时阻止相关高风险输出并转人工。
- **审计服务**：记录谁在何时基于何种授权确认了什么参数，调用了哪些版本的规则、模型和适配器，交付了哪个文件。

同一套 AI 逻辑可以复用，但会话不自动跨人、跨公司、跨群共享。跨渠道绑定必须由已登录经纪完成；群 ID 不能当作唯一用户 ID。Dify 的 `user`、`conversation_id` 由后端维护映射，不能由客户端任意指定后直接信任。Dify 官方要求 API Key 只在后端使用。[Dify API 指南](https://docs.dify.ai/en/api-reference/guides/get-started)

新 Dify 与员工实例分别管理管理员、密钥、数据卷、备份和权限。既有知识只迁移审核通过且有权对渠道披露的内容，记录来源、产品版本、生效日期和失效日期；不直接复用全部员工知识库。

## 4. 通道落地矩阵

| 通道 | 计划用途 | 必须验证的条件 | 失败或超限时 |
| --- | --- | --- | --- |
| APP 内 IM | 主会话、历史消息、任务状态入口 | 现有 APP 技术栈、SDK 支持、消息存储地域、身份映射、推送能力 | APP 内任务列表可主动查询 |
| H5 | 首期参数确认与计划书下载 | APP 登录衔接、微信内浏览器兼容、下载权限 | 同一任务可回 APP 查看 |
| 微信客服 | 外部经纪单聊问答与任务入口 | 回调验签解密、拉取消息与游标机制、去重、回复时窗与额度、转人工 | 提示回 APP 查看结果，保留任务 |
| 企微客户群 | 分享入口、固定 FAQ 与经验证的运营功能 | 逐项核对群类型、自动回复是否有开发接口、发送权限与频率、是否需成员确认 | 人工分享入口，不阻塞核心业务 |
| 企微内部智能机器人 | 符合成员管理条件时的可选入口 | 成员身份与实际使用方式、可见范围、官方接口支持范围 | APP/H5 |

经纪能否成为企业成员是组织和使用方式问题，不是给一个账号就能解决个人微信客户群接入的问题。会话存档与发消息权限也应分别核验，不能因为可以读取存档就推导出可以自动回复。

融云官方文档确有 Dify 类型的机器人回调，因此可列为 APP IM 的候选。是否选用仍取决于 APP 适配、地域、成本和权限链路；不要为省掉后端而绕过本项目的授权与审计。[融云机器人文档](https://docs.rongcloud.cn/platform-chat-api/bot/overview)

OpenIM 作为自建候选，需要单独评估部署、升级、消息可靠性、离线推送与值班成本。自建消息服务也不自动保证客户端推送等外部依赖均留在公司控制域内。

## 5. 数据、责任与策略层

### 5.1 部署前的数据流清单

逐项登记：数据类别、来源、用途、处理方、处理地域、存储地域、保留期限、删除方式、备份位置、运维访问与合同依据。范围至少包括聊天、客户资料、知识文档、embedding、模型请求、PDF、RPA 截图和错误日志。

“DeepSeek”需明确是外部 API、第三方托管还是自部署模型。通过香港 Dify 调用外部模型仍然会把请求发送给该提供方；只删除姓名也未必足以匿名化。不要把消费端隐私政策直接当作企业 API 的数据处理合同。

对内地与香港之间的数据流，应按实际处理活动、个人信息类别、数量与适用豁免判断义务。网信办规定区分不同出境情形，且出境机制的豁免不等于全部个人信息保护义务消失。[网信办规定](https://www.cac.gov.cn/2024-03/22/c_1712776611775634.htm)

香港私隐专员公署提供 AI 个人资料保护框架，并于 2026 年发布智能体隐私指引；可作为项目评审参考。是否满足 PDPO 取决于数据处理安排，不能由机房所在地区单独推定。[私隐专员公署 AI 资料页](https://www.pcpd.org.hk/english/artificial_intelligence/index.html)

### 5.2 最小控制

- 经纪登录核验之外，查询具体客户、保单、理赔和 PDF 时逐次检查所属公司、客户授权或服务关系、业务角色。知道手机号或 caseId 不代表有权查询。
- 登录凭据、会话 Cookie、API Key 只进入受控密钥存储和授权执行进程，不能放进提示词、审计正文、代码库或群聊。
- 群内通知采用最少信息，例如“任务已完成，请登录查看”；不把客户健康信息、保单详情或可直接下载的长期公开链接发进群。
- 审计保留应有明确期限和访问权限。必要证据留痕，日志中的敏感内容脱敏，不默认无限期保存所有原始聊天和截图。
- 对产品收益、保证与非保证利益、退保、适合性等内容使用经审核规则和引用；资料不足时明确缺口，不补造结论。
- 涉及建议的最终输出先完成必要审查再发送；若先通过 SSE 流出再扫描，已经发出的内容无法撤回作为有效拦截。

Dify 已有审核扩展和插件机制，但保险业务规则、授权控制、审计证据和人工审批仍是项目工作。`enforce_compliance()` 在本文中只是自建策略服务的命名约定。[Dify 审核扩展示例](https://marketplace.dify.ai/plugin/leslie2046/moderation)

### 5.3 软件授权

Dify 当前许可证允许一定商业用途，同时对多租户环境及前端标识有附加条件，并将其语境中的租户定义为 workspace。面向多家经纪公司交付前，应按实际 workspace、托管和前端使用方式核对许可证；业务系统多公司与 Dify 多 workspace 不是同一个判断，不能简单认定都免费或都收费。[Dify LICENSE](https://github.com/langgenius/dify/blob/main/LICENSE)

## 6. P1 开发任务书

### 6.1 MVP 范围与建议技术栈

目标：一家保司、一个已确认版本产品、表单输入、参数复核、异步任务、受保护的演示 PDF 下载。自然语言抽取接口保留，允许先作为实验能力，不阻塞表单链路。

工程建议：Node.js + TypeScript 业务后端；Playwright 独立 Worker；复用 APP 登录；H5 schema 表单；PostgreSQL 作为任务与审计事实源；Redis/BullMQ 作为可选任务调度组件；香港私有对象存储或获准的等效方案。版本在初始化时锁定并验证兼容性。

本地演示可以使用 SQLite 持久化任务和单 Worker，禁止把纯内存队列当作可交付任务记录。数据库写入与调度之间采用可恢复设计，例如 outbox 或持久任务轮询，避免“接口接受成功但任务丢失”。

### 6.2 参数 schema

每个 schema 至少包含：`productId`、`insurerId`、`schemaVersion`、官方产品版本、适用日期、字段定义及跨字段约束。保存每次任务实际使用的完整版本快照。

字段需覆盖真实门户要求。特别核实投保年龄口径、是否需要出生日期、性别、吸烟状态、币种、缴费频率、每期保费、缴费年期、保障年期和附加险。不要根据示例自行杜撰产品范围或默认值。

- 金额保存为十进制定点值或字符串，如 `"10000.00"`；币种独立必填。格式归一化和 schema 校验由确定性代码完成。
- `false` 是有效的非吸烟答案，不得当成缺失；未知值与用户明确否定必须区分。
- 缺少关键参数时追问；相互矛盾时标记冲突；跨字段校验失败时不能创建执行任务。
- 姓名称谓可以形成性别候选，但不能直接作为门户中被保险人性别的已确认值。
- 产品别名只能映射到经过维护的产品目录；旧版本或下架产品必须提示，不自动换成新产品。

用户给出的样例“陈先生35岁不吸烟、盈御3、年缴1万美元5年缴”，在目录存在对应产品的前提下，应提取：年龄 35、非吸烟、USD、年缴保费 10000、缴费年期 5；“陈先生”的身份指向、被保险人性别和实际产品版本仍需依据字段规则复核。LLM 不生成利益演示、回报率或现金价值数字。

### 6.3 确认与 API 契约

保留原有五类接口，补上可验证的确认记录和受保护下载。下表是建议接口，不是已实现能力。

| 接口 | 核心契约 |
| --- | --- |
| `GET /api/products` | 返回当前经纪有权使用的产品、版本、可用状态 |
| `GET /api/products/{id}/schema` | 返回带版本的 schema、限制和产品来源信息 |
| `POST /api/extract` | 输入 `productId, schemaVersion, text`；输出候选 `params, missing, conflicts, evidence`，不直接启动 RPA |
| `POST /api/proposal-drafts` | 服务端校验参数，保存不可变快照；返回 `draftId, revision, paramsHash` 和确认页数据 |
| `POST /api/proposals` | 用户确认后提交 `draftId, revision, paramsHash`，附 `Idempotency-Key`；成功接受返回 HTTP 202 与 `jobId, status` |
| `GET /api/proposals/{jobId}` | 校验归属后返回状态、时间、脱敏错误、`artifactId?` 和是否模拟 |
| `GET /api/proposals/{jobId}/download` | 再次鉴权；代理下载或签发短期下载链接 |

后端从可信登录会话取得 `tenantId` 和 `brokerId`，不信任正文中的身份字段。提交确认时必须读取服务端快照并比对版本；参数变化或确认过期后重新确认。审计记录确认人、时间和参数 hash。一个任意的 `confirmed: true` 不构成充分确认记录。

同一租户和经纪下，相同幂等键及相同请求返回原任务；相同键配不同请求返回冲突。重复消息或接口重试不能重复创建保司任务。随机 jobId 不能代替资源授权。

### 6.4 任务状态与恢复

```text
queued → running → validating → succeeded
             │          │
             ├──────────┴──→ awaiting_manual
             └─────────────→ retry_wait → queued
                             或 failed
```

Worker 记录租约、心跳、尝试次数与阶段。重启后检查未完成任务；不要把 `running` 任务直接当作可安全重做。任务已在门户生成但本地未记账时，应先检查门户结果或转人工，防止重复执行。

只自动重试明确的暂时性故障。参数错误不重试；登录过期、验证码、MFA、门户改版或结果不确定进入人工处理。限制单门户账号并发，隔离不同经纪的浏览器上下文与文件目录。

RPA 超时不应占住用户聊天请求。Dify 工具调用业务接口取得 jobId 后返回；用户可查询任务，Worker 完成后由业务事件触发通知。通知也应去重、可重试，并独立记录投递结果。

### 6.5 Adapter 与官方 PDF 核验

建议约定：

```ts
interface InsurerAdapter {
  login(input: {
    credentialRef: string;
    brokerId: string;
  }): Promise<SessionHandle>;

  generate(input: {
    session: SessionHandle;
    jobId: string;
    productId: string;
    productVersion: string;
    schemaVersion: string;
    confirmedParams: Record<string, unknown>;
  }): Promise<GeneratedArtifact>;

  close(session: SessionHandle): Promise<void>;
}
```

`SessionHandle` 是受控进程中的会话句柄；`GeneratedArtifact` 应包含内部文件引用、官方来源、生成时间、门户任务标识（如有）及核验元数据。浏览器状态、凭据和门户临时签名 URL 不直接返回给客户端。

真实 adapter 只在明确授权范围内工作。优先使用稳定的 label、role 等语义定位，并加页面和字段断言；视觉定位可辅助诊断，但不允许在金融参数页面自动改写流程后无校验继续提交。验证码和门户访问控制转人工或按保司允许机制处理，不以绕过风控作为稳定性方案。

交付前检查：文件确为 PDF、来源和产品版本匹配、关键参数与已确认快照一致、下载未跳回登录页、文件未串到其他任务。提取关键字段应使用经过验证的解析逻辑；无法可靠核对时转人工，不能仅凭 LLM 说“看起来正确”就交付。

保存原始文件及校验值，不改写官方利益演示。文件留存或代理下载须符合保司授权与使用条件；不允许留存时另行设计受控访问方式，不把临时门户 URL 当作永久产品接口。

### 6.6 mock 与真实环境分离

mock adapter 生成或读取本地演示 PDF，文件和界面显著标注“模拟文件，不构成保司计划书”，状态接口返回 `isMock: true`。不返回不存在的假 URL，不将模拟文件伪装成官方文件。

生产环境禁止静默回退到 mock。正式产品缺少真实 adapter 时返回不可用；生产配置误启 mock 时启动失败或阻止正式任务创建。

## 7. 实施顺序与验收

| 阶段 | 交付 | 验收门槛 |
| --- | --- | --- |
| P0：边界与底座 | 通道能力清单、独立 Dify、审核知识、登录授权、数据流、基础审计 | 未登录与越权请求被拒绝；知识来源可追溯；模型与数据地域明确 |
| P1a：可运行演示 | schema 表单、确认、持久任务、mock PDF、查询下载 | 完整链路可运行；模拟标识清楚；重启不丢任务；重复提交不重复执行 |
| P1b：真实保司试点 | 一家保司一个产品真实 adapter、文件核验、人工接管 | 官方样本逐字段比对；异常不误发文件；账号和任务不串用 |
| P2：渠道扩展 | APP 完整 IM、微信客服、自然语言抽取与确认 | 多轮身份映射正确；回调重放不重复执行；回复受限时仍可回 APP 查看 |
| P3：进度与通知 | 内部只读 API 或获授权的数据同步、事件通知 | 查询按客户关系授权；展示来源与更新时间；通知重复、失败和乱序可处理 |
| P4：运营扩展 | 更多产品、监控、备份恢复、容量与隔离增强 | 达到试点约定的成功率、交付时延及恢复目标后才扩量 |

鉴权和审计从 P0 开始，P4 只做增强。计划书和进度抓取可以共用账号会话、监控与调度基础设施，但通常需要独立页面流程和授权验证，不能把计划书 adapter 视为天然支持进度查询。

排期保留为条件估算：P0 可参考 1–2 周；P1a 可按第一周任务执行；P1b 应在取得真实字段、样本与门户访问后再估。v1 的 2–4 周只能作为有经验团队、单产品且账号授权就绪时的参考，不能作为包含第三方开通等待的承诺。

### 第一周可直接执行的工作

1. 初始化后端、H5、配置和持久任务库；明确开发身份与生产登录适配边界。
2. 建示例产品 schema 和两类目录接口，显著标注示例产品。
3. 完成表单、服务端校验、参数快照与确认页。
4. 完成幂等创建任务、独立 Worker、状态查询和异常状态。
5. 接 mock adapter，生成可下载的模拟 PDF，完成下载授权。
6. 加抽取接口及可替换的模型调用层；缺少密钥时明确返回未配置，不能伪称已调用模型。
7. 运行下面的核心验收并提交操作说明、环境变量示例、限制清单。

### 核心验收用例

- 非吸烟 `false`、金额单位、必填币种和冲突参数按 schema 正确处理；抽取不补造缺失字段。
- 确认后篡改参数、schema 或 draft revision 被拒绝；正常修改须重新确认。
- 其他经纪或其他租户取得 jobId、draftId、artifactId 后仍不能访问资源。
- 相同幂等请求只运行一次；Worker 中断后能恢复或转人工，不直接重复门户提交。
- 验证码、会话过期、门户改版和 PDF 字段错配都不会产生“成功交付”的状态。
- mock 在生产被阻止；真实 PDF 无法可靠核验时进入人工处理。
- 文件下载经过权限检查；日志中没有密钥、Cookie 或完整客户敏感信息。
- 真实试点另建经人工核准的样本集，覆盖金额、年龄、缴费方式边界和异常路径；明确样本数量、可接受差异和通过标准后执行。

## 8. 待补输入与当前可推进范围

| 输入 | 用途 | 未取得时可以继续做什么 |
| --- | --- | --- |
| 经纪的组织关系与客户授权方式 | 定账号、租户及数据范围 | 定权限接口和使用模拟身份验收 |
| APP 技术栈、登录协议、现有 IM 情况 | 定集成方式与 IM 选型 | 做独立 H5 与后端契约 |
| 一份脱敏真实计划书及对应官方字段、产品版本 | 确定真实 schema 与核验规则 | 做显式示例 schema；不能声称已支持该真实产品 |
| 保司授权范围、测试账号、演示工具页面与 MFA 流程 | 开发真实 adapter | 做接口、mock、任务恢复和人工接管 |
| 内部保单/理赔/进度 API 或数据来源 | 开发进度能力 | 定只读接口及授权契约 |
| 模型、IM、存储和运维地域要求 | 验证留港或公司控制域承诺 | 做数据流清单与部署候选 |
| 企微后台权限与官方收发接口实测 | 确认群及单聊能力 | APP/H5 首期不受阻 |

凭据通过项目的密钥管理流程配置；方案和聊天中不收集明文保司密码。真实字段、授权和账号尚未具备时，mock MVP 可以完成，但真实保司上线保持未完成状态。

## 9. 差异化指标

以可核验的服务结果替代未经证实的竞品判断：官方来源可追溯比例、确认参数与 PDF 一致率、计划书端到端成功率、P95 交付时延、异常发现及恢复时间、人工介入率、跨租户越权测试结果、审计记录完整率。

对外定位可采用：“为经纪提供官方计划书生成、授权查询和可追溯的业务辅助。”只有数据流和合同验证通过后，才加入“数据留港”或“公司控制域内处理”的明确承诺。
