# Dify 工作流实施计划 v1

## 结论与时间

Dify 从当前阶段立即开始，不等待香港 Python 文件。第一版用现有本地业务 API 和模拟计划书执行器完成闭环；香港脚本到位后，只替换计划书执行适配器。

| 时间 | 交付 |
| --- | --- |
| 第 1 天 | 香港 Dify 环境、DeepSeek 模型、服务端密钥、三个应用骨架 |
| 第 2 天 | 经纪助理 Chatflow：意图识别、知识问答、无法核实的安全回复 |
| 第 3 天 | 参数抽取 Workflow：产品 Schema、缺失项、冲突项、证据片段 |
| 第 4 天 | 合规审查 Workflow：硬规则、建议性内容审查、审计输出 |
| 第 5 天 | 接入当前 APP 后端、回归样例、失败分支、发布测试版本 |
| 香港 Python 可用后 1–2 天 | 将模拟执行器替换为第一家保司的真实适配器并做沙箱验收 |

## 架构边界

```text
APP / 企业微信
      │
      ▼
业务后端（身份、租户、客户权限、确认、任务、审计）
      │
      ▼
Dify（理解、检索、编排、回复草稿、合规扫描）
      │
      ├── 知识库
      └── 业务后端工具接口
                │
                └── 香港 Python / 保司门户
```

Dify 不保存保司账号，不直接信任前端传入的 brokerId、clientId，也不决定客户是否有权读取某份保单。身份和数据范围由业务后端验证。Dify API Key 只放在后端。

## 工作流一：`broker_assistant_chat`

类型：Chatflow。负责多轮对话与统一入口。

### 输入

- `query`：经纪输入
- `conversation_id`：Dify 会话标识
- `actor_token`：后端签发的短期工具令牌，不包含账号密码
- `client_id`：可选，使用内部编号
- `channel`：`app`、`wechat_service`、`wecom_group`

### 节点

1. **用户输入**：接收问题和后端上下文。
2. **问题分类器**：分为知识问答、生成计划书、查询进度、客户跟进、无法识别。
3. **知识问答分支**：知识检索 → DeepSeek 依据检索结果回答 → 无资料时明确说无法核实。
4. **计划书分支**：调用 `proposal_extract`，返回已提取参数、缺失项和“去确认”动作；不在此处创建任务。
5. **进度分支**：HTTP 工具调用业务后端，只传短期令牌和 caseId；由后端做权限校验。
6. **变量聚合器**：合并各分支的候选回复。
7. **合规审查**：调用 `compliance_guard`。
8. **答案节点**：返回文本、引用、动作卡和审查编号。

### 输出

```json
{
  "intent": "proposal",
  "message": "已整理参数，还缺被保险人性别，请确认后再生成。",
  "citations": [],
  "action": {
    "type": "open_proposal_form",
    "payload": { "productId": "demo-savings-01" }
  },
  "compliance": {
    "decision": "allow",
    "auditId": "cmp_..."
  }
}
```

## 工作流二：`proposal_extract`

类型：Workflow。负责自然语言到产品参数，不计算计划书数字。

### 输入

- `product_id`
- `schema_version`
- `text`

### 节点

1. **HTTP 请求**：从业务后端读取该产品 Schema。
2. **参数提取器**：按 Schema 输出字段值。
3. **代码节点**：做确定性规范化，处理币种、金额格式、布尔值和枚举。
4. **代码节点**：计算 `missing[]`、`conflicts[]`、`evidence{}`。
5. **IF/ELSE**：有冲突时返回人工确认；缺字段时返回追问；齐全时返回确认卡。
6. **输出节点**：只返回结构化参数，不调用计划书生成接口。

### 输出契约

```json
{
  "productId": "demo-savings-01",
  "schemaVersion": "1",
  "params": {
    "age": 35,
    "smoker": false,
    "currency": "USD",
    "annualPremium": "10000.00",
    "paymentTerm": "5"
  },
  "missing": ["gender"],
  "conflicts": [],
  "evidence": {
    "age": "35岁",
    "smoker": "不吸烟",
    "annualPremium": "年缴1万美元"
  },
  "requiresConfirmation": true
}
```

### 强制规则

- “陈先生”不能推断被保险人性别。
- 同一句出现两个年龄、币种或缴费年期时进入 `conflicts`。
- 金额由代码节点规范化；LLM 不做收益、现金价值或保费计算。
- 提取结果不能直接触发 RPA；业务后端必须生成参数哈希并由经纪确认。

## 工作流三：`compliance_guard`

类型：Workflow。负责所有对外回复的统一出口检查。

### 输入

- `draft_reply`
- `intent`
- `citations`
- `product_id`
- `channel`

### 两层审查

1. **确定性红线**：代码节点检查禁用承诺、无来源数字、伪造出处、越权信息、敏感字段和未标明的模拟内容。
2. **语义审查**：DeepSeek 判断是否把一般资料写成个性化投保结论，是否遗漏重要限制，是否超出检索资料。

### 决策

- `allow`：原样输出。
- `rewrite`：改成有出处、有限定语的专业回复，再次跑确定性规则。
- `block`：不给用户错误内容，返回人工处理提示。

每次输出 `auditId`、规则版本、命中规则、原文哈希和最终回复哈希。完整原文是否留存由法务和数据保留政策决定。

## 业务后端需要补的接口

| 接口 | 作用 |
| --- | --- |
| `GET /api/products/{id}/schema` | Dify 获取当前产品字段定义 |
| `POST /api/dify/tool/progress` | 查询进度，后端执行身份和数据范围校验 |
| `POST /api/dify/tool/compliance-audit` | 保存合规判定与回复哈希 |
| `POST /api/dify/callback` | 接收受签名保护的异步结果 |
| `POST /api/proposal-drafts` | 保存已规范化参数并生成确认快照 |
| `POST /api/proposals` | 经纪确认后创建计划书任务 |

当前原型已经具备最后两个接口。新增工具接口统一放在鉴权网关后，使用短期服务令牌、时间戳、nonce 和请求签名，避免把长期业务密钥配置在工作流变量里。

## 知识库组织

第一版建立四个独立集合：

1. 产品条款与官方说明。
2. 内部操作流程和服务规范。
3. 合规红线与批准话术。
4. 保司门户操作手册，只供运营，不进入经纪问答。

文档元数据至少包含 `insurer`、`product_id`、`document_type`、`version`、`effective_date`、`jurisdiction`、`audience` 和 `status`。已失效资料禁用，不与现行版本共同召回。

## 第 5 天验收样例

1. “陈先生35岁不吸烟，年缴1万美元，5年缴”能抽出五个字段，性别保持缺失。
2. 同时出现“5年缴”和“10年缴”时必须提示冲突。
3. 未在知识库找到的产品利益问题必须回答“无法核实”，不能补写数字。
4. “保证赚”“绝对安全”等表述被改写或拦截。
5. 未经经纪确认，系统中不能创建计划书任务。
6. Dify 超时、模型限流和工具接口失败均进入失败分支，返回可理解提示并记录审计。
7. 不同经纪不能通过修改 clientId 查询他人数据。
8. 同一问题在 APP 与后续微信通道的答案结构一致。

## 上线门槛

- 用不少于 50 条匿名化问题做回归，其中至少 20 条为红线或冲突样例。
- 参数提取以字段准确率和整单完全正确率分别统计。
- 知识问答必须返回资料来源；没有来源不回答产品事实。
- 每次 Workflow 发布保留版本号、变更说明和回滚版本。
- 先在内部测试空间运行，再开放给少量签约经纪试用。
