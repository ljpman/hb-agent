# 保险经纪智能体 · 分阶段交付计划 v1

日期：2026-09-21。状态：规划完成。用户补充：几家保司的 Python 文件已经可用，放在香港电脑，目前不方便提供。已知所在设备地域，尚未取得代码目录、结构或运行证据；本目录目前只有文档。无需为完成本次规划立即取回代码。

本计划承接用户认可的“官方计划书＋讲解包＋轻量客户跟进卡”，保留原方案的知识问答、完整 APP IM、进度查询与多渠道方向。实施原则改为：先盘点和复用现有 Python 能力，再补产品化能力，不重新开发已经可用的保司脚本。各阶段的“验收”是项目交付标准，不表示相关功能已通过检查。

## 1. 做完之后是什么效果

首期用户是一组已登录、已授权的渠道经纪。经纪从 APP 进入客户记录，填写或用自然语言描述需求，确认参数后取得保司官方计划书；随后获得带出处的讲解包，经纪复核后导出客户版。该次沟通、计划书版本和下一步跟进任务留在客户跟进卡中。

正常路径：选客户 → 描述需求／填表 → 补齐并确认参数 → 提交生成 → 查看任务状态 → 打开官方 PDF → 核对讲解包 → 导出客户版 → 记录下次跟进。

异常路径：字段不明确时追问；保司登录或页面异常时转人工；PDF 无法核实时暂停交付；讲解包核对未通过时保持草稿。经纪能看到具体状态，运营能接手处理。

### 首期必须有

| 功能 | 首期做到什么程度 | 经纪看到的结果 |
| --- | --- | --- |
| 官方计划书 | 先选现有脚本中最稳定的一家保司、一个产品作贯通样板；封装已有能力，补参数确认、异步任务、核验和鉴权下载 | 可查、可下载的官方 PDF，或明确的待处理状态 |
| 讲解包 | 一页摘要、约三分钟讲解提纲、常见问题、来源页码；支持经纪修改、复核和导出 | 一份可用于准备客户沟通的材料，客户版有清晰标识 |
| 客户跟进卡 | 客户标识、需求备注、计划书版本、内部跟进阶段、下一动作及时间 | 同一客户的工作记录集中可见 |
| 产品问答 | 首个产品经审核的条款、手册和 FAQ；回答带出处，过期或不足则提示 | 常见问题可自助查询 |
| APP 完整 IM | 历史、多轮、任务卡片、已读或送达能力按 SDK 验证、离线推送、多端会话隔离 | 能持续使用的聊天入口，刷新或换设备后能恢复记录 |
| 运营后台 | 任务队列、异常接管、产品与知识版本、讲解包版本、审计查询 | 能处理失败、追溯结果和维护资料 |

现有其他保司脚本全部纳入盘点和保留，按测试通过情况逐一启用；“一个样板”只限定首次贯通和验收顺序，不要求删掉或重写已有多保司能力。跟进卡中的“客户考虑中／待跟进”属于经纪工作记录，不伪装成保司实时状态。资料补齐后，通过后续接口接入自动业务进度。

多产品官方方案对比、语音工作备注转需求卡、材料预检、保单／理赔进度同步、微信客服单聊。企微客户群按经过验证的官方能力接入；客户群自由 AI 对话不作为首期依赖。

## 3. 七步实施路线

排期是本项目规划估算：按 **1 名前端／APP 工程师＋1 名后端／AI 工程师＋1 名 Python／集成工程师** 可并行工作，业务负责人和测试／运维提供固定支持。若现有脚本可稳定复现、输入输出清晰且无需大改，首期试点暂按 **6–8 个开发周** 规划，含集成、修复与试点；代码盘点后重估。原来从零开发的 8–10 周估算不再作为当前基线。账号、采购、授权等外部等待另列；团队少于该配置时重新排期。

| 步骤 | 参考时间 | 怎么做 | 阶段交付 | 通过条件 |
| --- | --- | --- | --- | --- |
| 1. 定流程、契约与样板 | 第 1 周 | 当前先根据业务说明登记已有能力，定义页面、参数确认、讲解包和 Python 调用契约；代码可用时补静态盘点 | 需求和接口草案、页面流程、待验证矩阵、首期任务 | 可以用显式模拟服务继续开发；真实脚本能力保持待验证 |
| 2. 封装服务与业务底座 | 第 2–3 周 | 将 Python 能力接到统一接口／Worker，补登录、确认、持久任务、表单与后台 | H5 → 任务 → 已有脚本或显式 mock → 文件的流程 | 参数确认、权限、重复提交和重启恢复通过；真实与模拟清楚区分 |
| 3. 验证真实保司链路 | 第 3–4 周 | 使用现有登录、填表与下载逻辑，补缺失的核验、隔离、异常接管；逐一验证已有保司 | 样板真实链路及各保司可用状态表 | 已授权场景输出正确官方文件，错误能接管且不误报成功 |
| 4. 做讲解包与跟进卡 | 第 3–5 周，可并行 | 建可信事实表、讲解模板、复核导出、客户版本与待办记录 | 讲解包及客户跟进卡 | 数字有证据、修改可追溯、版本不串、客户间隔离 |
| 5. 接 APP、Dify 与通知 | 第 4–6 周 | 接完整 IM、账号映射、问答、抽参数、任务卡片和推送 | APP 内完整交互 | 手机端能从会话完成全流程，重复回调不重复办任务 |
| 6. 小范围试点与上线 | 第 6–8 周 | 5–10 位经纪连续试用，记录错误、耗时和人工介入，演练恢复 | 首期试点报告、操作说明、上线与回退包 | 全链路就绪后开始试点，关键验收通过，业务负责人接受结果 |
| 7. 扩产品与能力 | 首期通过后另排 | 先第二产品与方案对比，再按实测痛点加语音、预检、进度和微信客服 | 每批一个可验收增量 | 对应数据及权限就绪，前一批质量达标 |

第 4 步可先用经审核的样本开发，最终验收要绑定第 3 步生成的真实文件。第 5 步的 SDK 选型和 APP 登录勘查从第 1 周开始；正式联调等底座稳定后进行。

香港代码暂不可取时，先做第 1 步、第 2 步的通用底座及第 4 步的样稿／页面。第 2 步真实脚本封装、第 3 步和真实文件验收等待香港侧配合。上述周数是资料及对接条件具备后的开发参考，不表示从今天起倒数就一定上线。

三个交付节点：**第 2–3 周看统一入口调用现有脚本；第 4–5 周看真实 PDF＋讲解包＋跟进卡；第 6–8 周看经纪在 APP 中的试点结果。** 周数以代码复用顺利和输入到位为前提；有些能力若已存在可前移，不能在未读代码前认定需要重做。

### 第一步完成标准

1. 形成已知／待验证 Python 能力矩阵，明确样板候选、字段、代码维护、解释内容和验收负责角色；具体人员待落实的单列。
2. 真实产品开发前需至少一组“官方输入参数 ↔ 官方 PDF”的可核对样本，初始目标为 3–5 组；暂缺时第一步可交付模板并进入模拟开发，真实产品门槛保持未完成。
3. 参数表写明必填、选项、金额单位、年龄口径、跨字段限制和未知项，不自行补造规则。
4. 经纪能沿页面流程说明自己在哪确认参数、在哪看进度、在哪复核讲解包。
5. 登录、任务归属、文件访问、人工接管与部署地域有明确设计和负责方。
6. 后续任务有负责人角色、依赖和验收条件；外部等待不隐藏在“开发中”状态里。

第 1 周预计得到的七份交付：现有能力与缺口清单、需求清单、样本与字段表、页面原型、讲解包样稿、统一调用契约、开发与验收清单。本次交付的是这些工作的计划与填写模板，代码盘点、原型及真实样稿尚未完成。

## 5. 模块具体如何实现

### 5.1 业务后端先确定任务和权限

现有 Python 脚本保留语言和已验证的自动化库；不会为了统一技术栈强行改写成 TypeScript 或 Playwright。若已有 Python Web 服务就优先扩展它；若只有独立脚本，可加 Python HTTP 服务及 Worker。现有 APP 已有后端时，可以保留原后端，通过内部契约调用 Python 执行服务。D4 先定可替换的调用边界，真实服务选型在代码盘点后确定。

数据库保存任务事实；调度器只负责唤起执行。队列可先从单 Worker 开始，后续按实际并发增加，不以模型或聊天记录充当任务库。

统一调用边界至少包括 `productId`、schema 版本、已确认参数、`jobId` 和凭据引用，输出内部文件引用、来源及核验元数据。若原文件只有 CLI 入口，用固定命令与结构化输入封装，禁止把用户文字或模型输出拼接成 shell 命令。需要进程隔离的库留在独立 Worker，不直接塞进 Web 请求进程。

服务端校验产品参数并保存不可变草稿；经纪确认草稿版本后才创建任务。按经纪及机构检查客户、计划书、讲解包和下载权限。重复提交返回原任务；门户执行结果不确定时先核对或转人工，不直接重跑。

主要数据实体：机构、经纪、客户／客户引用、需求草稿、计划书任务、文件、已核实事实、讲解包版本、跟进事项、审计事件。每个实体有明确归属；最初只有一家机构也保留隔离设计。

### 5.2 现有 Python 的封装和加固

代码可以继续留在香港，服务层与 Worker 也可在获准的香港环境部署，再由业务后端经受控网络调用；不要求把代码或客户资料搬到当前电脑。现有香港电脑可用于初步验证，是否适合长期运行要检查供电、网络、系统维护、账户隔离和运维安排，不能直接视作生产服务器。具体请求、响应、状态和错误边界见《Python 对接契约草案》。

先将每个现有脚本映射到会话建立、产品选择、字段填充、提交生成、下载／获取、核验和清理七步；已有能力只包一层明确契约，缺失部分补齐。字段映射与产品 schema 分离，门户页面变化不直接改变业务参数语义。

若已有脚本使用 Playwright，可利用语义定位和显式页面断言；其自动等待能减少页面时序问题，但不能证明选对产品或金融参数，仍需业务校验。若使用其他已稳定运行的工具，不因这一建议自动迁移。[Playwright 定位文档](https://playwright.dev/docs/locators)

记录每阶段结果、脱敏错误和必要证据，限制同一门户账号并发。登录失效、验证码、MFA、字段含义变化与文件核验失败进入人工任务。关闭某个 adapter 应不影响已有文件下载及其他产品。

### 5.3 讲解包：先建可信事实，再生成文字

处理顺序：官方 PDF → 确定性解析／人工确认 → 带来源的事实表 → 经审核知识检索 → 生成解释草稿 → 规则与数值核对 → 经纪复核 → 导出固定版本。

可信事实至少记录 `artifactId`、文件 hash、`productVersion`、字段代码、原始值、单位／币种、保证属性、保单年度、PDF 页码及定位、核验方式。解析失败的数值不进入对客草稿。

讲解包固定包含：方案概况、缴费安排、主要保障、关键限制、保证与非保证利益的解释、3–5 条常见问题、来源引用、生成和复核版本。产品不适用的模块隐藏，不生成不存在的保障或数值。

数值和利益表由已核实事实填入模板；模型生成解释文字。输出中的数字、单位、保证属性、比较口径与引用关系再次校验。仅检查“数字是否在 PDF 出现过”不足以验收，因为同一个数字可能属于不同年度或不同利益。

对客导出需有明确“复核并导出”动作，保留审核人和版本。经纪编辑关键数字时要求重新确认来源；新版计划书生成后，将旧讲解包标记为旧版本，不能自动配到新 PDF。客户版标明辅助说明及原始文件来源，不替代或改写保司官方文件。

### 5.4 跟进卡：先做轻量工作记录

字段先限于客户标识、所属经纪、需求摘要、目标与预算（已确认／待确认）、计划书及讲解包版本、内部跟进阶段、下一动作、到期时间、经纪备注。

确认任务、生成完成和讲解包复核可自动形成时间线事件；备注和工作阶段由经纪编辑，保留修改记录。不自动猜测客户已同意或已投保。未来接内部客户系统时优先引用既有客户 ID，避免另建一套冲突档案。

首期提醒发给经纪。对客户的外发动作由经纪操作并遵守实际通道能力；不在规划中默认为系统自动群发。

### 5.5 Dify 工作流

建议保持三个清晰用途，使用同一套获准知识和规则版本：

| 工作流 | 输入 | 输出 | 业务后端的职责 |
| --- | --- | --- | --- |
| 产品问答 | 问题、产品版本、服务端确定的知识范围 | 答案草稿、出处、资料不足或需人工标记 | 限制资料范围，审核后发送，保存版本 |
| 参数提取 | 经纪文本、产品 schema | 参数候选、缺失项、冲突项、原文证据 | 确定性校验，生成确认草稿，禁止直接执行 RPA |
| 讲解草稿 | 已核实事实、模板、审核过的知识 | 分节讲解文字及引用 | 数值及语义核对、版本保存、经纪复核和导出 |

Dify 官方提供结构化参数提取能力，项目仍需自行完成领域校验和用户确认。[Dify 参数提取说明](https://dify.ai/blog/dify-ai-blog-workflow-major-update-workflows-as-tools)

聊天可保持多轮，但执行任务只读取已确认业务草稿。更换 LLM 或知识版本后运行同一套产品问答、抽取和讲解包回归样本。

### 5.6 APP、IM 与后端衔接

第 1 周确认现有 APP 技术栈、登录票据、客户 ID、已有消息服务和推送。已有合适 IM 时优先复用；尚无合适 IM 时，由 APP 负责人按技术栈、数据地域、费用和运维条件选择候选并完成小规模验证。

聊天消息先经过网关验签、去重和身份映射，再进入 Dify 或业务服务。业务任务状态回到任务卡片；IM 断线不丢任务。完整历史、多轮上下文、离线通知、多端一致性分别验收，不能仅凭消息能发出就认为 IM 已完成。

## 6. 页面与操作范围

首期经纪侧六个页面／视图：

1. **工作台**：待办、最近客户、生成中的任务。
2. **智能助理会话**：产品问答、提取参数、展示任务卡。
3. **参数确认**：字段、来源提示、缺失／冲突提示、确认提交。
4. **计划书任务详情**：状态、参数快照、官方 PDF、异常处理提示。
5. **讲解包预览**：来源跳转、编辑、复核、导出和旧版本提示。
6. **客户跟进卡**：需求摘要、文件版本、时间线和下一次跟进。

运营侧两个主要视图：任务队列与人工接管；产品／schema／知识／模板版本管理及审计查询。先做完成工作所需界面，指标大屏放在已有真实数据之后。

## 7. 验收与试点指标

以下数量和阈值均是建议的项目验收目标，须在第 1 周由业务和技术确认，不是当前实测结果或行业标准。

| 类别 | 首期目标与测量方式 |
| --- | --- |
| 官方 PDF 正确性 | 验收集至少 30 个经产品专家核准的有效参数场景；成功交付文件的关键字段与确认快照逐项一致。不能核实的文件不得标成功；统计自动核验及人工核验占比 |
| 异常处理 | 覆盖缺字段、矛盾、超范围、登录过期、验证码、门户页面变化、下载失败、文件错配、重复请求和 Worker 中断；正确拒绝或转人工 |
| 越权及版本 | 跨经纪／跨机构取文件、猜任务 ID、复用旧确认、跨会话串客户均被阻止；有验证记录 |
| 讲解包 | 至少 20 份不同参数／问题的样稿；交付版本关键数值、年度、币种、保证属性和出处全部核对通过；错误草稿被拦截 |
| 知识问答 | 至少 30 条业务审核问题，覆盖可答、资料不足、过期和冲突；按业务答案与引用判定，记录通过数及错误类型 |
| 试点规模 | 建议 5–10 位经纪，连续 7–10 个工作日，至少 30 个真实授权任务；分别记录自动完成、人工介入、取消和失败 |
| 自动完成率 | 暂定目标 ≥90%；分母为已接受的有效任务，用户主动取消单列；外部门户错误计入失败或人工，不能从分母抹去。小样本通过不代表长期 SLA |
| 交付时延 | 记录从确认到可下载的 P50/P95，包含排队；人工与自动单列。第 1 周测人工基线，第 3 步实测后再定具体时限 |
| 使用效果 | 经纪操作用时、讲解包修改用时、每单往返补问次数与现状比较；是否节省时间由实测判定 |
| 恢复与运营 | Worker 重启、通知重复、单产品暂停和备份恢复有演练记录；有人接收告警和处理人工任务 |

真实试点的每份对客讲解包仍由经纪复核。只要出现跨客户文件错配、越权泄露或错误关键数字被交付，立即暂停受影响功能，修复并重新验证后恢复。

## 10. 后续亮点的推进顺序

1. **更多现有保司／产品＋方案对比**：优先启用盘点中已经可用的其他脚本，在统一 schema 和文件核验通过后，按经纪确认的相同条件分别获取官方文件。规范保单年度、币种、缴费口径、保证属性与缺失项，再展示有出处的并排表；仅对真正缺失的产品编写新 adapter。
2. **语音备注转需求卡**：从经纪主动录制自己的工作备注开始，做转写、字段提取和确认；原音频是否保留、保留多久另行明确。确认前不自动改客户事实。
3. **材料预检**：基于一个产品的官方清单，先做缺件、缺页、清晰度、到期日和字段冲突；输出需经纪复核的清单，不承诺完成核保判断。
4. **自动进度和通知**：内部只读 API 优先；没有接口再验证获授权的数据同步。显示来源和更新时间，把内部工作阶段与保司状态分开。
5. **微信客服及客户群入口**：复用既有后端，核实企业账号实际权限、收发机制、回复限制和身份绑定后接入。外部群能力验证单独立项，不影响前面已完成的 APP 业务。

以上顺序是当前默认；如果试点数据表明补件或查进度更耗时，可调整后续批次，首期范围保持稳定。
