- 修改前离线基线为 199 项；本次改动后的最终完整离线测试结果见阶段 5。

## 阶段 3：后端 → Dify

已完成并由离线测试和真实 Dify 验收覆盖：

- 默认及严格／production 模式拒绝 Dify 环境变量；只有显式 `HB_DIFY_MODE=dev` 才接受 `localhost`／`127.0.0.1` Dify 地址。
- Chat、抽取、合规三个应用分别使用自己的 key；没有共享或替代 key。
- `extract()` 将后端会话映射生成的 `user` 传给 Dify；Dify 参数结果只做结构校验，业务参数和原文证据由后端确定性规则重算，且仍要求经纪确认。
- 对话、抽取及合规应用调用失败时写固定安全审计，不记录上游错误原文、密钥或 Dify `user` 标识。
- assistant 先等待完整 Dify 回复，再执行语义合规审查和确定性出口规则；语义审查只能收紧。`/api/bootstrap` 显示“M2b 开发联调版”。
- 没有知识库时，识别为 `knowledge` 的答复由后端固定为“无法核实”；语义审查 fail-closed 时的固定人工提示也明确说明“无法核实”。

## 阶段 4：Dify → 后端工具

**未接通。** 已验证 Dify API 容器能经 `host.docker.internal` 到达一个只监听本机回环的临时探针，不需要把后端绑定到局域网地址。仍未在 Dify 工作流启用合规审计或进度工具节点。

现有 gateway 要求短期令牌、由令牌生成的请求签名、时间戳、nonce 和数据范围。当前没有安全的方式把短期令牌交给 Dify 节点并避开工作流运行日志／模型输入中的凭据留存，也没有由后端把最小范围工具能力安全注入一次 Dify 运行的链路。因此没有在 DSL 中传递 token、没有提供绕过签名的替代接口，也没有放宽任何 gateway 校验。进度数据源仍未配置。
